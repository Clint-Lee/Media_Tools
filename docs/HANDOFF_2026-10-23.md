## 二、Astra 规划的采纳与反驳

### 2.1 采纳：抖音应止损

Astra 判断："按现有证据没有值得继续投入的免费匿名路线，应关闭常规探查任务"。
理由成立——失败的核心不是请求发不出去，而是**服务端不再提供目标字段**。

本轮确认的证据链：
- `play_count: 0` 同时 `digg_count: 1000` 正常 → 0 是隐藏占位，不是零播放
- 移动端 API、旧 iteminfo、第三方接口、签名注入全部已排除
- 签名（a_bogus/X-Bogus）只解决请求校验，**不能解密服务端返回的 0**

**决定**：从 P0 移除，官方授权流降为条件任务（需先确认字段/授权/费用再排期）。

### 2.2 采纳：最大风险是"证据链路失真"

Astra 指出：局部证据模块正确，不等于最终榜单正确。链路中任一处
`Number(null)`、`|| 互动数`、旧缓存读回，都会破坏"不伪造播放量"的承诺。

**本轮实测核实**：现有代码**没有**这类危险兜底（`playRaw` 全部用 `!== null` 严格判断，
`ranking.count` 用 `Number.isSafeInteger && >=0` 守卫）。风险是潜在的，不是现存的。
因此把工作从"修 bug"转为"建门禁防未来"。

### 2.3 反驳：`numericCount` 不存在

Astra 建议用 `numericCount`，实际项目导出的是 `readMetric`。已按其语义包装适配。

### 2.4 反驳：token 缓存修复不必要

Astra/初判认为小红书"不带 xsec_token 必失败 → 需要 token 缓存机制"。
**实测推翻**：发现流 `redVideo` 已经正确保留 `xsec_token`（真实数据 16/16 全带），
`red.get` 拿到带 token 的链接后 100% 成功（133-228ms）。

我最初测到的失败，是我自己用了**过期的历史笔记 ID（无 token）**，不是产品缺陷。
**因此没有实施 token 缓存，避免了无用改动。**

## 三、本轮实际修复的 2 处真实缺陷

### 缺陷 1：`note-not-video` 语义被污染

**位置**：`lib/public-view-evidence.js` 的 `redViews`

**问题**：原判断有运算符优先级坑——
```js
if(!id || noteId!==id || note.type!=='video' && !note.video) → 'identity-mismatch'
```
`&&` 先结合，导致**图文笔记（身份完全正确）也被判为"身份不匹配"**。

实测证据：
```
6aade08f000000002901531e  type=normal  status=identity-mismatch  like=2.3万
6a8745f90000000025004e24  type=normal  status=identity-mismatch  like=4.2万
```
这些笔记 ID 都对、互动数都真实，只是图文内容。

**修复**：拆成两个独立分支
- 真正的身份不符（`!id` 或 noteId 与 URL id 不一致）→ `identity-mismatch`
- 身份正确但非视频 → **新增 `note-not-video`**，并记录 `noteType`

### 缺陷 2：发现流条目不产出 `viewEvidence`（真实数据断层）

**位置**：`lib/platform-rankings.js` 的 `redVideo`

**问题**：小红书发现流条目只有 `playRaw: null`，**没有 `viewEvidence`**。
导致前端无法区分三种完全不同的情况：
- 没核验过（`not-checked`）
- 核验了但平台不给（`not-provided`）
- 是图文笔记（`note-not-video`）

实测：修复前 16/16 条 `viewEvidence = undefined`。

**修复**：`redVideo` 现在产出
```js
{ playRaw: null, viewSource: 'xiaohongshu:discovery-feed',
  viewEvidence: { status: 'not-checked', source: '...', field: 'none', observedAt: ... } }
```
后续 `red-public` 取到详情后会覆盖为真实证据状态。

实测：修复后 13/13 条都有 `viewEvidence`，状态分布 `{not-checked: 13}`。

### 缺陷 3：`enrichPublic` 全局单飞，导致并发不同 list 时第二个完全丢失

**位置**：`lib/red-public.js` 的 `enrichPublic`

**问题**：`if(browserJob)return browserJob.promise;` 把整批锁住。
并发传入两个不同 list 时，第二个直接拿到别人的 promise，**自己的一条都不抓**。

实测证据：
```
并发调用 enrichPublic(list1) 与 enrichPublic(list2)
调用后缓存命中: 批1=5/5, 批2=0/5    ← 批2 完全丢失
```

**修复**：axios 阶段**不加锁**（`get()` 自带 `pending` 去重 + `failures` 30s 退避，天然安全），
只有浏览器兜底阶段才单飞（稀缺资源才需要）。

实测修复后：批1=5/5、批2=5/5，总耗时 3264ms → **347ms**。

### 缺陷 4：核验覆盖率 0% —— 时序错误 + 慢路径

**位置**：`lib/public-discovery.js` 的小红书分支

**问题**（两个叠加）：
1. `notes.prefetch(pool.list)` 是**不 await 的后台任务**，紧接着 `map` 就执行，
   `peek()` 永远读到核验**之前**的状态 → 前端只能看到 `not-checked`
2. `await enrichPublic(...)` 只在 `timeRange!=='all'` 时才跑，默认路径完全不等

另外 `enrichPublic` 本身用的是**浏览器顺序导航**（8s deadline、只取 6 条），
而 `get()` 的 axios 快路径实测只要 **18ms/条**。

实测性能对比（真实网络）：

| 方案 | 12 条总耗时 | 成功率 |
|---|---|---|
| 浏览器顺序导航 | 8s 内跑不完 6 条 | — |
| 顺序 axios | 2250ms | 100% |
| **并发 axios（6 并发）** | **217ms** | **100%** |

**修复**：
- `enrichPublic` 改为**两阶段**：先并发 axios（6 并发、6s 预算、上限 20 条），
  全部成功则**不启动浏览器**（省掉几秒冷启动）；仅失败项走浏览器兜底（4s 预算）
- `public-discovery` 里改为 `await notes.enrichPublic(pool.list)`，再 `map` 回填
- 新增 `enrichStats()` 暴露 `{axiosTried, axiosOk, axiosFailed, browserTried, browserOk, elapsedMs, timedOut}`
- `remember()` 成功后 `failures.delete(id)`，避免浏览器兜底成功但 axios 仍被 30s 退避锁住

实测修复后：
```
发现 17 条 | 已核验 17/17 | notChecked 0 | enrich 耗时 704ms
enrichStats: {axiosTried:17, axiosOk:17, axiosFailed:0, browserTried:0, elapsedMs:704}
```

**并发上限取值依据**（实测三档均零失败）：

| 并发 | 20 条耗时 | 成功/失败 |
|---|---|---|
| 6 | 1ms（缓存命中） | 6/0 |
| 12 | 271ms | 12/0 |
| 20 | 222ms | 20/0 |

取 6 而非 12/20：瓶颈本就不在并发数，而上游反爬按 IP 聚合瞬时并发打分，
保守值留容错余量，收益几乎为零、风险不对称。

## 四、新增的证据链路门禁

**文件**：`test/view-evidence-pipeline.test.js`（22 项断言，已接入 `npm test`）

覆盖链路：**证据校验 → 归一化 → 缓存往返 → 排序 → 数据质量 → enrich 契约**

| 不变量 | 断言内容 |
|---|---|
| I1 | 无有效播放证据 → `playRaw === null`，绝不被补成数字 |
| I2 | 互动数（赞/评/藏/享）只能进互动字段，不得冒充播放 |
| I3 | 无证据的播放值不得进入播放排名 |
| I4 | 以上规则经 JSON 缓存往返后仍成立 |
| I5 | `enrichPublic` 对非小红书链接不发请求；空列表安全返回 |

关键用例：
- 抖音 `play_count=0` + 点赞 1000 → 播放仍为 `null`
- 抖音正数播放 123456 → 保持不变（真实值不被误伤）
- 身份不匹配时即便有正数播放也拒绝
- 小红书 WatchAction 1345 == 1047+240+58 → 识别为互动合计并拒绝
- 图文笔记 → `note-not-video`，**不等于** `identity-mismatch`
- 发现流条目 → `not-checked`，可区分"没查"与"平台不给"

### 反向验证（证明门禁真有效）

写了注入脚本 `.cache/verify-test-catches-bug.js`：
故意把 `redViews` 改成"零占位时用 `digg_count` 冒充 `playRaw`"，
**测试确实失败**；还原后恢复通过。

这条验证很重要——它证明门禁不是摆设。

## 六、环境踩坑（给下一位）

1. **`node_modules` 为空**：`hotVideo` 分支检出后需 `pnpm install`。
   不装会报 `Cannot find module 'globe.gl'`（server.js 第 31 行 `require.resolve`）。
2. **`live-sources` 的 `withPage` 是注入依赖**，不是内部 require。
   调 `publicFeed` 必须传 `{withPage: live.withPage, memo: async(k,w)=>w()}`，
   否则报 `withPage is not a function`。
3. **`publicFeed` 的 platform 在 `options` 里**：`{platform:'xiaohongshu', ...}`。
4. **发现流每次返回不同笔记**（推荐轮换），所以跨次调用缓存命中率低，
   这是设计特性不是 bug。同一轮内 `peek()` 有效。
5. **`redVideo` 读 camelCase**（`noteCard`/`xsecToken`/`interactInfo`/`displayTitle`），
   真实数据也是 camelCase。测试造数据别用 snake_case，否则测不出真实行为。
6. **Puppeteer 脚本跑完必须 `process.exit()`**，否则浏览器不关，命令挂起。
