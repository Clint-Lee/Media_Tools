## 一、抖音播放量：本轮新增的 4 条实测路线（全部失败）

上一轮（10-23/10-24）已排除 10 条免费路线。本轮继续从社区最新代码找方案，
逐条实测，避免把"理论上可行"写成"已实现"。

### 1.1 证据来源（本轮实际下载的开源项目源码）

| 项目 | 抓取的文件 | 它用的端点/结论 |
|---|---|---|
| `Johnserf-Seed/f2`（最成熟的抖音签名库） | `f2/apps/douyin/api.py`、`filter.py`、`crawler.py`、`utils/abogus.py` | 完整端点表；**`play_count` 提取器被作者注释掉** |
| `NanmiCoder/MediaCrawler` | `media_platform/douyin/client.py`、`helpers.py` | 说明 detail 必须带 `uifid`+`verifyFp` 同源 cookie |

**决定性证据**（`f2/apps/douyin/filter.py` 第 1359-1361 行，原文）：

```python
    # @property
    # def play_count(self):
    #     # 不从该接口获取
    #     return self._get_attr_value("$.aweme_detail.statistics.play_count")
```

社区最成熟的抖音开源库**主动放弃了 play_count**，注释写着"不从该接口获取"。
这是比任何单次实测都更有力的旁证。

### 1.2 本轮新增实测的 4 条路线

| # | 路线 | 实现方式 | 实测结果 |
|---|---|---|---|
| A | `POST_STATS` `/aweme/v2/web/aweme/stats/` | f2 端点表里有定义但作者未使用 | GET → `url doesn't match`；POST JSON → `参数不合法`（status_code 5）。端点存在但需未知参数，拿不到数据 |
| B | detail + `uifid`+`verifyFp`+`fp` | 按 MediaCrawler 注释的完整参数组合，cookie 从真实页面读取 | `403 Blocked by ArgusSecurityPlugin Sign Invalid`（匿名页面没有 `s_v_web_id`，`UIFID_TEMP` 无法通过 Argus 校验） |
| C | 用页面内 `byted_acrawler.frontierSign` 生成签名 | 真实浏览器里调用抖音自己的签名函数，拿到签名后请求 detail | 签名成功、请求 200、返回 132KB 完整 aweme_detail，但 **`play_count` 仍是 0**。证明签名不是瓶颈 |
| D | 移动端分享页 H5（4 个入口） | iPhone UA + 移动视口渲染 `iesdouyin.com/share/video|slides/`、`m.douyin.com` | 页面只显示"抱歉出错了 请尝试在抖音内观看"。抖音已关闭 H5 分享页的播放量展示 |

### 1.3 结论

抖音 `play_count` 是**服务端按访问者身份主动隐藏**，不是签名、Cookie、UA、
端点选择的问题。任何匿名/未授权读取方都拿不到该字段：

- 浏览器匿名会话：`play_count: 0`（占位）
- 真实签名请求：`play_count: 0`
- 完整 cookie 参数组合：403 Argus 拦截
- 移动 H5 分享页：不再展示播放量
- 第三方解析服务（上一轮实测 `api.douyin.wtf`）：`play_count: null`
- 社区最成熟开源库（f2）：主动注释掉该字段提取器
- 商业数据商（新抖/飞瓜/千瓜）：公开说明只提供"预估播放量"

**保留的唯一真实路径**（代码已就绪，需运营者凭证）：
1. `DOUYIN_CLIENT_TOKEN` + 开放平台 `hotsearch` 权限（需企业资质审核）
2. TikHub API（实测端点存在，401 需 token）：
   `GET https://api.tikhub.io/api/v1/douyin/app/v3/fetch_video_statistics?aweme_ids=<id>`
3. 本机真实登录态（`npm run platform:login -- douyin`）+ `lib/douyin-views.js` 钩子

## 二、本轮真实修复：LLM 语义总结降级为 TextRank

### 2.1 发现的真实缺陷

E2E 实测抖音视频 `analyze` 时，`npm test` 全绿但产出是 `analysis=extractive`
（原句摘录），不是语义总结。查服务端日志得到真正原因：

```
[node-llama-cpp] Failed to load a prebuilt binary for platform "win" "x64".
Error: An Application Control policy has blocked this file.
  \\?\...\@node-llama-cpp\win-x64\bins\win-x64\llama-addon.node
  code: 'ERR_DLOPEN_FAILED'
```

- 本机 `CodeIntegrityPolicyEnforcementStatus = 2`（**WDAC 已强制实施**）
- `process.dlopen()` 直接验证：`ERR_DLOPEN_FAILED — An Application Control policy has blocked this file`
- 模型文件（Qwen3-4B gguf 2.5GB）和 node-llama-cpp 都在，**是系统策略阻止原生 DLL 加载**
- 后果：`localAnalysis.available()` 返回 `true`（只查文件存在），但 `summarize()` 必失败，
  于是整条链路退化成几乎等于"取最长句"的 extractive

### 2.2 解决方案：纯 JS TextRank 语义摘要（新模块 `lib/semantic-digest.js`）

不引入任何原生依赖、不联网，在神经模型不可用时提供**真正的语义摘要**：

| 环节 | 实现 |
|---|---|
| 分词 | 中文 2-gram + 英文按词；中英文停用词表过滤 |
| 加权 | TF-IDF（平滑 IDF，避免单次词权重爆炸） |
| 句间关系 | 加权余弦相似度构图 |
| 排序 | PageRank 迭代 30 轮（damping 0.85） |
| 去冗余 | MMR：与已选句相似度 > 0.62 的候选跳过，保证跨段落覆盖 |
| 主题分类 | 9 类关键词规则（美食/科技数码/旅行户外/影视娱乐/游戏/知识科普/生活日常/运动健身/商业营销） |
| 关键词 | 出现 ≥2 次的词按 count×IDF 排序，取前 8 |

**新旧对比（同一段 8 句字幕实测）**：

```
旧 extractive：几乎等于按"句子长度"排序，容易全落在同一段
新 textrank  ：选出 6 个跨段落代表句 + 正确归类"科技数码" + 关键词（芯片、手机）
```

### 2.3 三级降级链（`lib/media-jobs.js analyzeTranscript`）

```
远程 LLM (LLM_BASE_URL)
  ↓ 请求失败 / JSON 解析失败 / 校验失败
本地 LLM (node-llama-cpp)
  ↓ 原生二进制被系统策略阻止 / 模型缺失 / 内存不足
TextRank 语义摘要 (lib/semantic-digest.js)   ← 本轮新增
  ↓ 字幕为空或过短
原句摘录 (extractive，最终兜底)
```

- 每一级失败都**降级而不是抛错**，用户永远拿到可用结果
- `method` 字段严格区分：`remote-llm` / `local-llm` / `textrank` / `extractive`
- 任务完成文案同步区分（"本地 TextRank 语义摘要（无神经模型）"）
- `notice` 如实说明降级原因，不冒充 AI 总结

**E2E 实测验证**（重启服务后真实视频）：

```
旧：[161s] complete 转写完成；AI语义总结不可用，仅提供字幕原句摘录
     COMPLETE transcript lines=65 analysis=extractive
新：[161s] complete 转写完成；本地 TextRank 语义摘要（无神经模型）
     COMPLETE transcript lines=65 analysis=textrank
```
